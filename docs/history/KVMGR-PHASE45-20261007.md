# Phases 4–6: the disk tier cannot be built at this layer, and the blocker is not the one the plan names

Phases 1–3 of the own-KV-manager plan are built and green. **Phases 4 and 5 — the
disk tier — cannot be delivered as specified**, for a reason that is structural
rather than a matter of effort, and the plan's own justification for choosing the
broad approach turns out not to hold. This records the evidence, because the
conclusion is worth more than another attempt.

## The plan's argument, and why it does not reach

The plan chose to write a whole KV subsystem partly for this reason, which it
called "the strongest" and "a structural reason, not a preference":

> vLLM's own offload design routes every tier through a **CPU primary tier**
> (`CPUOffloadingSpec`/`TieringOffloadingSpec`), and on unified memory a CPU
> buffer is **zero-sum** — `cpu_bytes_to_use` comes straight out of the KV pool.
> Reusing upstream's tiering therefore cannot give us disk without first paying
> for RAM we do not have. A manager of our own writes **GPU → disk directly** and
> skips the hop.

The premise about `cpu_bytes_to_use` is correct. The conclusion does not follow,
because **a KV cache manager cannot write KV bytes at all.**

## FINDING: the manager layer holds no KV bytes. None.

`KVCacheBlock` is metadata and nothing else — `block_id`, `ref_cnt`,
`_block_hash`, two free-list pointers, `is_null`. There is no tensor, no device
pointer, no view.

And it is not just that one class. Across the whole layer this plan builds on —
`patch6` (1,855 lines), `patch7` (546), the pristine `kv_cache_coordinator.py`
(689) and `kv_cache_manager.py` (601), **3,691 lines** — a case-insensitive
search for `torch`, `tensor`, `cuda`, `device` or `kv_caches` returns **exactly
one hit**, and it is the word "safetensors" inside a comment added by this work.

	patch6 … 1   <- "safetensors_e8m0" in an MNT-11 comment
	patch7 … 0
	kv_cache_coordinator.py … 0
	kv_cache_manager.py … 0

The KV tensors live in the **worker** processes' GPU memory, addressed by
`block_id`. The manager is a bookkeeper that decides *which* block ids a request
owns; it never touches their contents. So "our manager writes GPU → disk
directly" is not a harder version of Phase 4 — it is not expressible at this
layer. Writing KV bytes requires worker-side code, which is precisely what a
`KVConnector` is, and `vllm/v1/kv_offload` already is one.

This is the same shape as the process-boundary finding in Phase 2 (a stat logger
cannot see the manager's counters because it runs in the API server process).
Both come from the same place: **the plan was written against the manager layer,
and two of its deliverables live in other processes.**

## FINDING: the real blocker is vllm#45663, and nothing we build moves it

The repo had already established this and the plan does not mention it.
`docs/local/status/INCIDENTS.md` — "KV disk-offload is not viable on this
model/version (parked 2026-09-14)", re-checked 2026-10-04:

| | state | |
|---|---|---|
| vllm#43093 | **closed as "not planned"** | the crashes are not fixed; upstream declined |
| **vllm#45663** | **open, stale, no fix** | **the disqualifying one** |
| vllm#56772 | not re-checked | MLA+DSA TP-dependent row sizes |

**#45663 is the wall.** The sparse indexer's `fp8_fp4_mqa_logits` materialises
every KV block at once instead of chunking, so with offloading on it **OOMs past
~120K tokens** against a working set of **570K**. That is a failure in the
*attention* path, triggered by blocks not being resident — so it would hit **any**
offload design, including one that skipped the CPU tier entirely. Writing our own
writer does not avoid it; it arrives at it from a different direction.

**#43093 names our own topology**, which is worth keeping in view:
`gpu_block_size=64 not divisible by hash_block_size=256`. The offload path hashes
on 256-token blocks while one of the five KV groups uses 64, so it is the
**hybrid group layout** that breaks the transfer. Phase 0 found the same number
from the other side: `lcm_block_size` is 256 and the five groups are
256/64/64/4/8.

## What this does NOT change

The prize is real and unchanged, and it is why this is worth re-checking rather
than abandoning. From the current boot: KV is **6.92 KB/token**, so a 570K prefix
is **4.04 GB** against a recompute of **~518 s**. Breakeven is **7.8 MB/s**; NVMe
does 4 GB in **~1.3 s**, and both nodes have **2.9 TB free** — roughly 700 such
prefixes. A ~400x win on the cold path, and it would stop an engine restart
costing every client a full cold prefill.

**And Phases 1–3 do not depend on any of it.** They attack the same problem from
the other end: keeping a prefix that is *already* resident, which is where
retention is decided and which the manager layer genuinely owns. The measured
373,833-token total loss happened with KV usage at **22–33%** — the pool
two-thirds empty — so it was never a capacity problem that disk would have
solved. It was a policy bug, and that is what Phase 3 fixes.

## What was built instead

Nothing speculative. The three `disk_*` knobs stay in the table and **refuse
loudly**, carrying the reason:

	kvmgr: disk_enabled=True REFUSED -- a KV cache manager holds NO KV BYTES …

A fingerprint module was **not** written. The plan specifies one, and it is the
right requirement for any future tier — KV bytes are valid only for the exact
engine that wrote them, and vLLM's block hash covers token ids and the previous
block's hash, not the engine config, so a restore across a changed config returns
plausible tensors that decode to nonsense with nothing crashing. But a
fingerprint with no writer and no reader is a guess at an interface that does not
exist yet, in a layer that has turned out to be the wrong one. It belongs with
the writer, wherever that ends up living.

## Phase 6, the coordinator layer: assessed, and it does not help either

The plan sequences Phase 6 last and says explicitly it "might turn out to be
unnecessary, and that is a finding, not a failure". It is unnecessary **for the
work in this plan**, for two separate reasons:

1. **`spec_manager_map` already gives manager-level control**, which is what
   Phases 1–3 needed and used. Owning `KVCacheCoordinator` would add nothing to
   them.
2. **The coordinator holds no KV bytes either** — 0 hits in the search above. So
   it does not unblock Phase 4/5. It is the same layer, one level up.

What the coordinator *does* own is worth recording, because it is the one place a
future change would have to go:

- **`find_longest_cache_hit`'s fixed point.** The hit length converges to the
  **minimum across all five groups**. This is why a group-0-only disk restore
  would buy nothing (Phase 0, finding 1), and it is coordinator logic, not
  manager logic.
- **`lcm_block_size`** (256 here) and the 256-token hit alignment.
- **`verify_and_split_kv_cache_groups`**, which decides which `manager_cls` is
  asked for a hit — and is the reason registering in `spec_manager_map` is
  enough to be reached.

So the honest answer to "should we own the coordinator too" is: **not for this**.
If the disk tier is ever revived it will be at the **worker/connector** layer, and
the coordinator is where the group-minimum problem would then have to be solved.
