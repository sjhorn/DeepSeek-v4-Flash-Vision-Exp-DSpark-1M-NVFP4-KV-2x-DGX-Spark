## Notes

- **PR vllm#46995 is in v0.31.0** (verified). The merge commit is `f5a8d73377d0`, merged 2026-07-01; GitHub compare `f5a8d73...v0.31.0` returns `ahead`, behind_by 0. In 0.31, though, DSV4 DSpark runs only on Model Runner V2 (`v1/worker/gpu/spec_decode/dspark/`). Our production runs DSpark on the V1 runner, and our notes say "do not set VLLM_USE_V2_MODEL_RUNNER=1". The out-of-scope overlays (`gpu_model_runner.py`, `v1/spec_decode/dspark*.py`, `scheduler.py`) therefore have no counterpart in 0.31's V1 runner. That one decision shapes the whole port.
- **sm_121 / GB10:** 0.31 supports the 12.x family (`is_device_capability_family(120)` in the b12x MoE and `platforms/cuda.py`). The b12x attention backend accepts `(12,0),(12,1)` explicitly (`backends/b12x.py:215`), and the b12x docs name SM120/SM121. DSV4 on SM12x defaults to FlashInfer sparse MLA. That needs a FlashInfer build with flashinfer#4380, or the layer raises at init (`flashinfer_sparse.py:661-668`). The o_proj runs through DeepGEMM `fp8_einsum` on SM12x. The old prototype found DeepGEMM MXFP4 "Unknown SF transformation" on SM120; whether 0.31's DeepGEMM fp8_einsum runs on GB10 is **not verified**.
- **NVFP4 KV:** upstream `nvfp4_ds_mla` is a different, SM100-only format. Reusing the name for our 584 B DSV4 envelope would collide with `KVQuantMode.NVFP4_DS_MLA` semantics in 0.31. Our Stage C page is byte-for-byte the fp8_ds_mla page size. Whether the 0.21 image actually stores NVFP4 data in it, or the pool advantage comes from the `KVQuantMode.NVFP4` side effect on other specs, is **not verifiable without the image**. The README claims a pool difference ("pick for pool size").
- **B12X:** upstream now ships b12x linear (`kernels/linear/*/b12x.py`), MoE (`fused_moe/b12x.py`, MXFP4 + NVFP4) and paged attention (`backends/b12x.py`). It does not ship b12x mHC, the WO projection, or MLA decode.
- The base-image deltas in non-overlaid files (for example `attention.py` `setup_b12x_wo_projection`, `envs.py` B12X vars, `VLLM_TRITON_MLA_SPARSE`) are outside this inventory, but any CARRY of the WO projection needs them.

## Total

- **Adopt upstream DSpark (MRv2) + fp8_ds_mla path:** about **18–42 h** of porting work for these files. This is code only and excludes cluster validation (boot, 1M context, 2/4/6 concurrency, acceptance).
- **Carry our DSpark + nvfp4_ds_mla instead:** about **33–73 h**. Most of that is moving dspark.py and the out-of-scope V1-runner pieces onto the MRv2 speculator interface; that estimate is the least certain.
