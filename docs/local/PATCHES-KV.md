## MNT-6a — retention is capped by the protected-block cap, not by KV size

**CORRECTED:** this section called the cap "Patch 5"; it is `MNT-6a`.

Measured 2026-09-14 with `local-ops/cache-pressure/`: retained ≈ protected cap + 5-7%.

| `PROTECTED_FRACTION` | cap (blocks/group) | retained tokens |
| ---: | ---: | ---: |
| 0.30 | 1,022 | 280,690 |
| 0.50 (current) | 1,707 | 457,079 |

Raising the fraction raises retention near-linearly. **Caveat:** the benchmark is sequential, so
its zero-preemption result does not prove 0.50 is safe for 2 concurrent 1M sessions — protected
blocks are withheld from new allocations. Watch `vllm:num_preemptions_total`; drop toward 0.30 if
it climbs.

> `MNT-6b`'s eviction on, a conversation's head reads **0.0% / 14.4s** after the session; with
> `MNT-6c` (`swa_recycle_cached: 0`) it reads **99.5% / 0.5s**, and the session itself is ~35%

**`MNT-6b` was investigated and exonerated.** Its `_maybe_evict_cached_block()` call on recycled
pages looked like a retention leak, but it is correct hygiene: only `ref_cnt == 1` pages (held
solely by that request) are recycled, and their stale hash mapping must be dropped because the page
is about to be overwritten. The recycling exists to *protect* other requests' prefixes from global
LRU churn. Do not disable `VLLM_SWA_RECYCLE_SKIPPED_BLOCKS` expecting better retention.

## MNT-8 / MNT-9 — gated on a file, not on env, so an arm costs no restart

Container env cannot change on a running engine, so an env-gated A/B costs one 250-600s cold boot
per arm and interrupts every session on the cluster. Both mechanisms therefore read
`/var/tmp/vllm-kv-flags/flags.json` (bind-mounted at `/etc/vllm-kv-flags`, re-stat'ed at most once
a second):

```bash
bash local-ops/kv-flags.sh                               # what each node is running
bash local-ops/kv-flags.sh free_queue_prepend_uncached 1 # arm B
bash local-ops/kv-flags.sh pin_static_head 1             # arm C
bash local-ops/kv-flags.sh reset                         # arm A (stock behaviour)
```

Rules that follow from the design:

- **The directory is mounted, not the file** — so an atomic replace (`os.replace`) is visible
  inside the container. `kv-flags.sh` writes that way; editing in place risks a half-written file.
- **A missing file, bad JSON or an unreadable path means every flag is OFF**, which is stock
  behaviour. That is the safe direction, and it is also why a torn write cannot silently produce a
  third arm.
- **`VLLM_<FLAG_NAME>` in the container env always wins**, so a boot can pin an arm if a run ever
  needs that. Nothing sets one today.
- **A flip applies to the next request only.** It does not re-order blocks already freed or
  un-pin what is pinned, so give an arm a fresh session rather than flipping mid-conversation.
- The start script creates the file OFF on both nodes if it is absent, and leaves an existing one
  alone — an arm survives a restart.

Both mechanisms' ordering and refcount logic are tested offline against the real vLLM classes,
no GPU and no restart: `HOST=spark-45ea bash local-ops/kv-mech-tests.sh` (13 checks — pin covers
exactly `[0, B)`, a re-pin is a hit rather than a second reference, the SWA groups pin only the
contiguous tail, the LRU trim releases the least-recently-reused head, and each flag is inert when
off).

**Unpatched sources** are tracked at `patches/pristine/`, and `patches/generated/*.patch` is our
delta against them — that is what to read when assessing an upstream patch, and it needs no cluster
access. Regenerate with `bash scripts/regen-local-patches.sh`.

**Rollback baseline:** `local-ops/baseline-20260914/` is a separate, older snapshot kept as a
rollback point — `MANIFEST.txt` (image id `sha256:4035bb5a…`, config, file hashes, mounts, boot
metrics) plus `pristine-vllm-files.tgz`.

> **Always re-pull a pristine file with `docker run --rm --entrypoint cat <image> <path>`.**
> Reading through a bind-mount gives you the *patched* file, not the original — that is how
> `local-ops/baseline-20260914/MISLABELLED-was-patched-single_type_kv_cache_manager.py` came to be
> filed as pristine for five days.

## MNT-10 — one long prefill takes the whole token budget, and everything behind it stops

**The failure.** vLLM's V1 scheduler walks `self.running` **in order** against **one shared**
`token_budget` (= `max_num_batched_tokens`, 8192 here):

```python
token_budget = self.max_num_scheduled_tokens
while req_index < len(self.running) and token_budget > 0:
    ...
    if 0 < self.scheduler_config.long_prefill_token_threshold < num_new_tokens:
        num_new_tokens = self.scheduler_config.long_prefill_token_threshold
    num_new_tokens = min(num_new_tokens, token_budget)
    token_budget -= num_new_tokens
```

`long_prefill_token_threshold` defaults to **0**, so the clamp is dead and a request still in
chunked prefill takes `min(remaining, token_budget)` — **all 8192**. The `while` guard then fails
and every request behind it is scheduled **zero tokens that step**. A decoding sequence needs about
six. It gets none.

**Measured on our own traffic**, 2026-09-20 19:33 → 2026-09-21 08:09, 696 ten-second windows of
real Claude-Code-with-subagents load. Full numbers and the worked two-minute example are in
[`status/INCIDENTS.md`](status/INCIDENTS.md); the short version:

| | |
|---|---|
| decode, single request, median | **36.0 tok/s** |
| decode per request, `Running=5`, p10 | **0.5 tok/s** |
| prefill : decode tokens | **12.4 : 1** |
| preemptions / max KV / hit rate | **0** / 71.5% / flat ~94% |

Zero preemptions with a flat hit rate is what separates this from both KV exhaustion and cache
loss — **it exonerated `MNT-6c` under load**, which was `CACHE-TEST.md` §10 item 1 and the only
real risk that fix introduced.

**Why it is gated rather than just set.** Stock already has the right knob; it is simply boot-only.
The scheduler re-reads the field on **every step**, so nothing but config plumbing forces a restart,
and the right value is genuinely unknown:

- [GLM-5.3-Flash-EXL3-2x-DGX-Sparks#110](https://github.com/MiaAI-Lab/GLM-5.3-Flash-EXL3-2x-DGX-Sparks/issues/110)
  — **our exact hardware** (2× DGX Spark GB10, TP=2 over RoCEv2, 1M context), same diagnosis to the
  same line. `1024` against `MNBT=2048` took a **440 s** freeze to **17.9–24.9 s**; cost **+10.6%**
  on the long prefill *under contention only*, nothing solo.
- [vllm#54919](https://github.com/vllm-project/vllm/issues/54919) — same symptom on 2-node DGX Spark
  TP2, open and undiagnosed. **Reports `4096` against `MNBT=8192` was not enough**, which is why our
  boot default is 2048 and not 4096.

Gating turns that sweep from a 250-600 s cold boot per arm into a live flip — the same trade that
made `MNT-8`/`MNT-9` affordable to test. **It paid for itself immediately:** the dose-response
curve below is four arms, measured in one sitting, for zero restarts.

### Measured dose-response (2026-09-21, `local-ops/starve-test.py`)

One "victim" streams a decode; once it is steady, an "attacker" fires a **uniquely stamped**
(therefore uncached) **144,027-token** prompt. Engine otherwise idle.

| `long_prefill_token_threshold` | victim tok/s during prefill | median gap | **max stall** | attacker prefill | prefill cost |
|---|---|---|---|---|---|
| **0** (stock, no cap) | **0.33** | 4.33 s | **5.17 s** | 82.8 s | — |
| 2048 | 0.95 | 1.20 s | 1.36 s | 87.3 s | +5.4% |
| **1024 (deployed)** | **1.55** | 0.67 s | **0.74 s** | 95.8 s | **+15.7%** |
| 512 | 2.53 | 0.41 s | 0.48 s | 123.4 s | +49.0% |

Monotonic, no overlap. Victim rate with no attacker present was 14.5 tok/s in every arm, so the
ratio column is like-for-like.

**Why 1024 and not 2048.** 2048 buys only 2.9x over stock; 1024 buys **4.7x** and takes the worst
stall from **5.17 s to 0.74 s** — the number a user actually feels — for 15.7% on a prefill that is
already the slow part. 512 costs +49% for a further 1.6x and is not worth it. This independently
lands on the same value as
[GLM-5.3-Flash-EXL3-2x-DGX-Sparks#110](https://github.com/MiaAI-Lab/GLM-5.3-Flash-EXL3-2x-DGX-Sparks/issues/110),
and confirms [vllm#54919](https://github.com/vllm-project/vllm/issues/54919)'s report that a cap of
half the budget is too loose to help much.

**What this does NOT establish.** A single victim against a single attacker on an idle engine. It
does not model several long prefills arriving together, which is what the 13h production trace
showed, nor the effect on aggregate throughput across many sessions.

> **That caveat turned out to matter: the curve above DOES NOT PREDICT REAL TRAFFIC.** It ranks 512
> best. On live traffic 512 is the **worst** of the three. See "Real traffic disagrees" below. Use
> the curve as evidence that the knob *works*, never as a guide to its value.

### Real traffic disagrees — 512 is the worst setting, not the best (2026-09-21)

Measured on a live Claude-Code session with two subagents, flipping the cap between blocks. Same
session, same workload, minutes apart:

| | 2048 (6 min) | 512 (11 min) |
|---|---|---|
| **aggregate decode, median** | **60.7 tok/s** | **37.5 tok/s** |
| decode inside a starved window | 4.5 tok/s | **1.0 tok/s** |
| low-decode windows | 7 / 39 busy | 11 / 58 busy |
| **engine stats-line gaps > 15 s** | **none** | **40 s and 80 s** |

The gaps are the alarming part: the engine emitted no `loggers.py:271` line for up to 80 seconds
while requests were running. That is the scheduler loop itself stalling, not decode being
descheduled.

**Why the synthetic curve was wrong.** At 512 a 144K prefill becomes **282 chunks**, each paying
fixed per-step cost — attention metadata build, indexer top-k, kernel launches — at ~140K context.
The curve already measured that as **+49% prefill duration**; what it could not show is that
everything else stays degraded for half again as long, which on real traffic outweighs the gentler
per-step sharing. The synthetic test had exactly one decoder to protect, so it only ever scored the
sharing half of the trade.

### Most "collapses" are NOT starvation — check `Running` before tuning

The single most useful thing found here, and it reframes the problem:

```
11:06:00  GEN  7.3  Running: 1
11:06:10  GEN  1.7  Running: 1     <- ONE request. Nothing is being starved.
```

`Running: 1` with near-zero decode means **the one request in the engine is itself prefilling** —
somebody waiting on their own prompt, not being crowded out. **No cap helps that case, and a
smaller cap actively hurts it**, because it makes that prefill slower. This is why 512 felt like a
regression to the user even though it "shares better".

At 2048, all 7 low-decode windows had `Running >= 2` (genuine starvation). Before reaching for this
knob, split low-decode windows by `Running`: only the `>= 2` ones are the problem `MNT-10` exists
to solve.

### 1024 vs 2048 is a TIE, and the A/B that tried to separate them was CONFOUNDED

An alternating four-block A/B (1024/2048/1024/2048, 5 min each) on live traffic returned 1024 ahead
at every matched concurrency — **and it is not usable**, because the arms did not receive
comparable work: the 2048 blocks carried **525,191** prefill tokens against the 1024 blocks'
**166,182**, a 3.2x imbalance. Four blocks was not enough to average out a workload that arrives in
bursts. One collapse also straddled an arm boundary, starting under 2048 and continuing into 1024,
so per-arm attribution is unsound at this block length.

Taken together with the block comparison above (1024 median 61.0, 2048 median 60.7) the two values
are **indistinguishable on real traffic**. The deployed value is 1024 because the synthetic curve
favours it on stall duration, not because it beat 2048 anywhere measurable. **Do not re-litigate
1024 vs 2048 without a much longer alternating run** — the region is flat and the variance is
workload-driven. Intermediate values such as 1536 are legal (no alignment constraint) and would be
expected to land inside the same noise.

**Retracted along the way:** an apparent regression at `Running=4` (12.5 tok/s aggregate vs a
pre-fix 68.8) was read off **n=2**. At n=7 it is **70.6** — no regression. And a matching
CUDA-graph hypothesis (that a tighter cap forces mixed prefill+decode steps out of graph-eligible
pure-decode steps) is **not supported**: it predicts 512 degrading gracefully, and 512 instead
produced multi-second loop stalls.

### The ceiling this knob cannot raise

The prefix cache was measured **live over a 20 s window** — 262,846 queries, 258,304 hits,
**98.3%** — so cache misses are not the cost. What remains is genuine: **each new subagent pays a
full cold prefill of its whole context, ~115-145K tokens, taking 90-140 s**, during which
everything decodes in the low single digits. 690K prefill tokens passed through in 20 minutes.

`MNT-10` makes that window survivable (4.7x on the synthetic victim) but cannot remove it. The
remaining levers are about **not paying the cold prefill**: warm-up
([`../../CACHE-TEST.md`](CACHE-TEST.md) 10, item 9) and the tools flap (item 8), both
client-side.

```bash
bash local-ops/kv-flags.sh long_prefill_token_threshold 1024   # try a tighter cap, live
bash local-ops/kv-flags.sh long_prefill_token_threshold 0      # disable the cap (restores the bug)
bash local-ops/kv-flags.sh reset                               # omits the key -> boot value, 2048
```

**Two deliberate differences from the other flags**, both because "no opinion" must mean *the boot
value*, never *0/disabled*:

1. `reset` does **not** write this key. With no key the engine falls through to
   `--long-prefill-token-threshold` from the compose (2048), which is the state we want.
2. A corrupt or half-written flags file returns the **last good** value, then the boot value. Every
   other flag reads a bad file as "off"; here that would silently restore the starvation.

**Verification after a restart — the boot log will NOT tell you.** The confirming `logger.info` in
`config/scheduler.py` sits inside a `max_num_partial_prefills > 1` branch, which is false for us, so
nothing is printed at our settings. Check these instead:

```bash
docker logs <container> | grep 'non-default args'        # must contain long_prefill_token_threshold: 2048
bash scripts/check-local-patches.sh <container>          # MNT-10 row must pass
docker logs <container> | grep 'MNT-10'                  # only if a flags/env OVERRIDE is active
```

The pre-flight that made this safe to deploy: the `long_prefill_token_threshold = 0` reset in
`config/scheduler.py` fires **only for encoder-decoder models** (we are not one), and the
`max_num_partial_prefills > 1` branch only *auto-fills a zero* — it does not clear a value we set.
